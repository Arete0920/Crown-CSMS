# Priority #6 Selective Expansion Canon

Status: Expansion governance policy
Updated: 2026-04-14

## Purpose

Define the next expansion layer after Priority #5 using strict Core/Modules/Add-ons discipline.
This canon governs sequencing, eligibility, and claims for later add-ons and standalone-capable products.

## Hard Guardrail

Core owns truth, Modules run school operations, and Add-ons integrate cleanly and can stand alone where proven.
Expansion work must not degrade or bypass Core truth paths.

## Priority Stack (Authoritative)

1. Core proof and release path
2. First-wave modules
3. Second-wave operational modules
4. First-wave add-ons and differentiators
5. Packaging, governance, and pilot-readiness
6. Later add-ons and standalone-capable expansion products

## 6A. Standalone-Capable Expansion (First)

Sequence these first because they create revenue engines, market differentiation, and optional product lines:

1. Crown Compass
2. Board Governance Suite
3. PD Hub
4. CRM / Marketing
5. Survey / Sentiment
6. Mobile App / Family App
7. Standalone Schedule Builder

## 6B. Mission-Distinctive Integrated Expansion (Second)

Sequence after 6A:

1. Chaplain / Pastoral Care
2. Portrait of the Graduate
3. Mission Metrics
4. Deeper Spiritual Life layers
5. Deeper Service and Outreach layers

## 6C. Integration and Partner Ecosystem (Third)

Build all later expansion as ecosystem-ready products, not hard-coded bolt-ons:

1. API-first contracts for each add-on capability
2. Event and webhook surfaces for integrations
3. Configurable workflows over custom per-school branching
4. Versioned integration compatibility policy
5. Integration runbooks and support ownership

## Standalone Qualification Gate

An add-on is standalone-capable only if all are true:

1. Tenant-safe auth and role model is explicit and tested
2. API contracts and role matrix are documented
3. Evidence tests and demo runbook are current
4. Packaging owner and support owner are assigned
5. Dependency map to Core truth paths is explicit and fail-closed

## Non-Negotiable Scope Rules

1. No Core schema or auth shortcuts to accelerate add-on delivery
2. No release claims beyond evidence state
3. No module bypass through add-on private data access
4. All deferred expansion remains explicit in release docs
