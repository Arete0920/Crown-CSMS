# Priority #7 Operating Company Canon

Status: Delivery and scale governance policy
Updated: 2026-04-14

## Purpose

Define the operating-company layer that follows Priority #6.
This canon governs implementation, support, integrations, release operations, and trust controls needed for repeatable school rollout.

## Priority Stack (Authoritative)

1. Core proof and release path
2. First-wave modules
3. Second-wave operational modules
4. First-wave add-ons and differentiators
5. Packaging, governance, and pilot-readiness
6. Later add-ons and standalone-capable expansion products
7. Implementation, support, integrations, and scale operations

## Governing Rule

After build and packaging, Crown execution shifts from feature expansion to repeatable delivery.
No operating-process shortcut may weaken Core truth, tenant safety, or release discipline.

## 7A. Implementation System

Each school implementation must follow a documented sequence:

1. Onboarding sequence with owner handoffs
2. Data import and migration process with validation gates
3. Configuration standards by Core, Modules, and Add-ons
4. Training plan by role (leadership, staff, support users)
5. Rollout checklist for pilot and production start
6. Pilot-to-live checklist with release-gate evidence

## 7B. Support and Customer Success System

Operate support as a repeatable function, not founder memory:

1. Issue triage workflow and intake channels
2. Severity levels and response-time commitments
3. Escalation rules from support to engineering
4. Client communication cadence and update policy
5. Knowledge base ownership and freshness checks
6. Customer health tracking and intervention rules

## 7C. Integration and API Ecosystem

Build connected-system capability as a governed layer:

1. Stable API contracts with version policy
2. Import/export standards and schema discipline
3. Integration runbooks per connector class
4. Partner connector governance and ownership model
5. Webhook/event design patterns and failure handling
6. Explicit Core/Modules/Add-ons boundary enforcement

## 7D. Release, Hosting, and Environment Discipline

Operate GitHub and Azure pathways as controlled systems:

1. Clean repo and release structure with canonical evidence paths
2. Staging/prod environment rules and promotion criteria
3. Monitoring and alerts tied to runbook actions
4. Deploy checklist with preflight, smoke, and postflight gates
5. Rollback and incident runbooks with ownership matrix
6. Secrets and config discipline with allowlist policy

## 7E. Compliance and Trust Layer

Establish durable trust posture before broad rollout:

1. Auditability of operations and release decisions
2. Role and tenant proof packs kept current per release
3. Privacy and compliance documentation maintenance
4. Security review cadence with closure tracking
5. Customer-facing trust and confidence materials
