## Review order

Review files in numeric order. Stop at the first failing required gate.

### PASS signals

Acceptable pass signals include:

- exit code 0 when shown,
- pytest `passed` summary with no failures/errors,
- npm/vitest pass summary,
- build completed successfully,
- explicit verifier PASS output,
- no unexpected stack trace or nonzero exit.

### FAIL signals

Failure signals include:

- traceback,
- `FAILED`, `ERROR`, `failed`, `error Command failed`,
- nonzero exit code,
- failed assertions,
- missing module/import,
- build failure,
- migration drift,
- route/API mismatch,
- timeout without pass summary,
- generated evidence file missing.

### UNKNOWN signals

Unknown signals include:

- truncated output without final status,
- command did not run,
- missing evidence file,
- tool output says skipped but not why,
- local environment unavailable.

Unknown is not pass. Unknown becomes `NOT VERIFIED`.

## First-failure decision tree

1. If repo state is dirty before evidence generation, classify as `repo_state`.
2. If Django check fails, classify as `settings` or `backend_contract`.
3. If migration check fails, classify as `migration`.
4. If tenant/admissions/aftercare/later-tier pytest fails, classify based on first failing test.
5. If npm install fails, classify as `dependency`.
6. If lint fails, classify as `frontend_lint`.
7. If frontend contracts fail, classify as `frontend_contract`.
8. If shell certification fails, classify as `dashboard_readiness` or `route_guard`.
9. If build fails, classify as `frontend_build`.
10. If release API contracts fail, classify as `api_contract`.
11. If navigation verifier fails, classify as `navigation`.
