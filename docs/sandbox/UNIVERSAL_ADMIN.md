# Owned presenter administration

The original Heritage school, open-session adapter and scenario remain intact.
The presenter reuses their real section-aware attendance, canonical enrollment,
tuition, progress-checkpoint, household verification and internal follow-up
implementation under normal password/JWT login, exact owned school, named
principal and existing school administrator role/permission checks.

After isolated local permission/core bootstrap, preflight and stage:

```sh
python manage.py prepare_universal_admin
python manage.py prepare_universal_admin --apply
```

Read-only preflight creates nothing. Apply refuses existing staging provenance
or either independently namespaced communication identity; it never adopts or
overwrites those records. The complete owner-authorized future provisioning
command and retained-generation rollover stage this scenario atomically with the
other modules. The shared Heritage student is never read or mutated.

The normal school-administrator page exposes the existing operational panel for
the closed presenter namespace with sandbox mode disabled. Its dedicated realm
is `/api/v1/presenter/admin/`: GET `state/` reads real owned records; POST
`resolve-operational-exception/` accepts an empty body and performs the existing
fixed fictional workflow. It verifies the household, marks the seeded attendance
exception EXCUSED and persists one internal MessageThread/Message. Repeated POST
is idempotent; reload reads the database. This records an internal communication,
not external email delivery. Presenter egress quarantine remains mandatory.

The server rejects other roles, foreign headers/selectors, revoked authority,
retired generations and unsafe runtimes. The mutation holds the owned root lock
so generation rollover cannot retire the actor between its checks and writes.
Communication Person/Household identities are UUID5 in that school's namespace;
they are not looked up or updated by potentially shared family name/email.
Historical messages, grades and attendance survive retained rollover. Destructive
bootstrap reset refuses this protected scenario instead of deleting history.

The surrounding dashboard's illustrative template tiles remain labeled sample;
they are not evidence for live business totals. The operational panel and actual
classroom/care/admissions workflows provide database-backed transactions.
General dashboard KPI certification, initial parent admissions/signatures and
full Camp clearance remain outside proven readiness. No Azure, production,
live provisioning/migration, new recurring resource, payment or credential
rotation is performed by this source increment.
